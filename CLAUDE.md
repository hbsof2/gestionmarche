# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A web platform for managing Algerian public procurement deals (Marchés Publics) — tracking raw materials, contracting authorities, their branches, contractors, deals, delivery receipts, invoices, users, and database backups.

## Tech Stack

| Layer    | Technology              | Local port | Hosting  |
|----------|-------------------------|------------|----------|
| Frontend | Next.js 16 + Tailwind 4 (CSS-first config, no `tailwind.config.js`) | 3000       | Netlify  |
| Backend  | Node.js + Express       | 5000       | Railway  |
| Database | PostgreSQL (Supabase)   | —          | Supabase |
| Storage  | Supabase Storage        | —          | Supabase |

## Architecture

### Frontend (`frontend/src/`)

**Navigation model** — `app/page.js` is the single-page shell. A `sections[]` array drives both the right sidebar and the top service bar. Two state values control what renders in the main content area: `activeSection` (which section) and `activeService` (which sub-action within the section).

**Section integration pattern** — implemented sections bypass the generic placeholder and render a self-contained `*Page` component. The parent passes `activeService` and `onServiceChange` as props so the top bar stays in sync. Example: when `activeSection === "raw-materials"`, `<RawMaterialsPage activeService={activeService} onServiceChange={setActiveService} />` renders directly. The `*Page` component watches `activeService` via `useEffect` to react (e.g. `"add"` opens the form modal, `"search"` focuses the search input).

**Data flow for each section:**
```
*Page (state: list, pagination, form open, delete modal, toast)
  ├── *List (pure display: table, search bar, pagination)
  ├── *Form (modal: field state + validation, calls uploadImage then create/update)
  └── *DeleteModal (confirmation dialog)
```
Receipts is the one exception to the page/offset pagination part of this shape — see "Receipts — default view and filtering" below.

**API client** — `src/lib/api.js` is an axios instance pointed at `NEXT_PUBLIC_API_URL`. A request interceptor attaches `Authorization: Bearer <token>` from `lib/auth.js`'s `getToken()` to every outgoing request. The response interceptor attaches `error.arabicMessage` so components can display Arabic errors without extra parsing, and additionally: a `401` calls `logout()` (clears `localStorage` and hard-redirects to `/login` — this is a real `window.location.href` navigation, not a Next router push, since a torn-down auth state shouldn't leave stale component state around); a `403` dispatches a `window` `CustomEvent("auth:forbidden", { detail: message })` instead of showing anything itself, because `api.js` is a plain lib file with no React/toast context — `app/page.js`'s `Dashboard` component is the one listener that turns that event into a floating toast. The `401` handler explicitly skips `/api/auth/login` requests (checked via `error.config.url`) so a failed login attempt shows its error inline on the login form instead of hard-redirecting and wiping it.

**Authentication** — `src/lib/auth.js` is the single source of truth for client-side session state, all backed by `localStorage` (`auth_token` / `auth_user`, both written by the login page on success): `getToken()`, `getUser()`, `isAuthenticated()`, `logout()`, and `hasPermission(permission)` (`true` unconditionally for `role === "admin"`, otherwise reads `user.permissions[permission]`). `app/login/page.js` is the only unauthenticated route — it redirects to `/` if already authenticated (mirrors the guard the other direction) and posts to `/api/auth/login` directly via `api` (not a service file, since there's no other auth-shaped call to share a module with). `app/page.js`'s `Dashboard` component gates the entire shell: a `checkingAuth` state renders a bare spinner until an effect confirms `isAuthenticated()` (redirecting to `/login` if not) and loads `getUser()` into state for the header's name/role badge and the sidebar's logout button (`logout()` from `lib/auth.js`).

**Service layer** — `src/services/<section>Service.js` wraps the axios calls. Components import from the service, never from `api.js` directly.

Key files:
- `app/layout.js` — sets `lang="ar" dir="rtl"`, loads Tajawal font, wraps `children` in `ThemeProvider`, and inlines an anti-flash-of-wrong-theme script in `<head>` that reads `localStorage.theme` and adds the `dark` class to `<html>` before hydration (`<html>` carries `suppressHydrationWarning` because of this intentional pre-hydration mutation — don't remove it)
- `src/lib/supabase.js` — anon-key Supabase client + `testConnection()` utility
- `src/lib/api.js` — axios instance with Arabic error interceptor
- `app/api/test-connection/route.js` — Next.js API route for connection health check
- `src/data/` — static reference datasets bundled with the frontend (e.g. `algeria-wilayas.js`: all 58 wilayas with their communes in Arabic, keyed by `code`). Import directly; these are not fetched from the API.

**Date fields** — every date input (`ContractorForm.jsx`: `birth_date`/`rc_date`, `ContractingAuthorityForm.jsx`: `rc_date`, `AuthorityBranchForm.jsx`: `rc_date`, `DealForm.jsx`: `start_date`/`end_date`) uses the same pattern instead of `<input type="date">`: three `<select>`s (day 1–31, Arabic month names, year range) backed by local `useState`, a `pad()` helper, and a `parseDate(isoDate)` helper that does `isoDate.split("T")[0].split("-")` to prefill from an existing record. On submit the date is built as a plain template-literal string (`` `${year}-${pad(month)}-${pad(day)}` ``) — **never** via `new Date(...).toISOString()`, which reintroduces the timezone-shift bug described in the `db.js` quirk above. List components display dates the same defensive way (`DealsList.jsx`'s `formatDate`: split on `"T"` then `"-"`, never `new Date(x).toLocaleDateString()`). Follow this exact pattern for any new date field.

**Searchable select** — `DealForm.jsx` has a local `SearchableSelect` component (type-to-filter dropdown over a fetched list, e.g. contractors/authorities) used for FK fields instead of a plain `<select>` with hundreds of options. Reuse or copy this pattern for future FK pickers rather than a native `<select>`.

**Deal detail / branches** — clicking a deal in `DealsList.jsx` opens `DealDetail.jsx` (full-page view, not a modal) showing the deal's linked `authority_branches` via the `deal_branches` join table. It has its own `BranchSearchableSelect` (same type-to-filter pattern as above) to add a branch, and calls `getDealBranches`/`addBranchToDeal`/`removeBranchFromDeal` from `dealsService.js`. A deal must always keep at least one branch — `removeBranchFromDeal` on the backend rejects removing the last one.

**Deal items (materials)** — `DealDetail.jsx` renders `DealItems.jsx` below the branches section (separated by a divider). Unlike the other sections, its add-form is **always visible** rather than opened via a modal/`activeService`, and stays open after a successful add (only the material/category selects are cleared — TVA and quantities are left as-is since the next line item often reuses them). It has its own local `SearchableSelect` for material/category pickers and inline-edit rows (click edit → the TVA/quantity/price cells become inputs with save/cancel, no modal) rather than a separate edit form. Fetches the full material list via `rawMaterialsService.getAll(1, "", 1000)` and the full category list via `materialCategoriesService.getAll()` (categories have no pagination at all — `getAllCategories` always returns the full array). All quantity displays (table cells, the browse modal's range display, `DealItemEditModal.jsx`'s pre-filled inputs) go through a local `formatQuantity`/`parseFloat(...).toFixed(2)` helper rather than raw string interpolation, since Postgres numeric columns come back as strings with variable precision.

**Deal item double-click edit modal + remaining-quantity tracking** — double-clicking a row in `DealItems.jsx`'s table (guarded with `!isEditing` same as the receipts table) opens `DealItemEditModal.jsx` — a small centered modal (not the inline row-edit, and not the browse modal) for editing `tva`/`min_quantity`/`max_quantity`/`unit_price` on that one item. Its read-only info card also surfaces consumption: `dealsController.js`'s `getDealItems` `LEFT JOIN`s `deal_items_snapshot` and returns `initial_max_qty`/`initial_min_qty`/`remaining_qty` (`COALESCE`d back to the `deal_items` row's own `min_quantity`/`max_quantity` when no snapshot exists yet, i.e. before the deal's first receipt) alongside every item; the modal derives `consumedQty = initial_max_qty - remaining_qty` (shown in orange) and colors `remaining_qty` green when it's still above 20% of `initial_max_qty`, red at or below that threshold — the same "still-available" framing `ReceiptDetail.jsx`'s add-material info box uses, just presented as three stacked rows instead of a live preview.

**Deal items browse modal** — the "تصفح" button in `DealItems.jsx`'s table header opens `DealItemsBrowseModal.jsx`: a full-list searchable popup (client-side filter over `items`/`categories` props, no extra API call) where each row expands inline into an edit form (CSS `grid-rows-[0fr]`/`grid-rows-[1fr]` transition, no JS height measuring) that — unlike the main table's inline edit — **also** lets you change the category. On save it optimistically patches its own local copy of the row and calls `onItemUpdated()` (parent's `fetchItems`) to refresh the table underneath without closing. Because of this, `dealsController.js`'s `updateDealItem` accepts an *optional* `category_id`: `SET ... category_id=COALESCE($5, category_id)` — sent by the browse modal, omitted by the main table's inline edit — so neither caller breaks the other.

**Deal statistics** — `DealStats.jsx` is a full-page view (like `DealDetail.jsx`, not a modal) reached either via the "إحصائيات" top-bar service (opens for the currently `selectedRow` in `DealsList.jsx`, or shows an Arabic "select a deal first" toast if none is selected) or a per-row purple `BarChart3` button. It fetches `getDealStats(dealId)` from `dealsService.js` (`GET /api/deals/:id/stats`, mounted before `/:id` in `routes/deals.js`), which returns `{ items, totals, deal }` — HT/TTC min/max totals computed in SQL by `dealsController.js`'s `getDealStats`, not recomputed client-side. Includes an Excel export (`xlsx` + `file-saver`, both frontend-only deps) producing a 3-sheet workbook (deal info, financial summary, itemized materials + totals row); exported numeric cells are rounded to 2 decimals via a local `round2()` helper and given an explicit accounting number format (`'#,##0.00'`, no currency symbol) via a local `applyNumberFormat()` helper rather than left as plain JS numbers/strings.

**Receipts — default view and filtering** — `receiptsController.js`'s `getAll` does not use page/offset pagination like every other section: with no filter query params it returns only the 10 most recent receipts (`ORDER BY created_at DESC LIMIT 10`); as soon as any of `contractor_id`/`authority_id`/`deal_id`/`branch_id` is present it drops the `LIMIT` and returns *all* matching rows instead, plus `filtered: true` in the response (the existing `search` param, matched against `reference`, layers on top of either mode). `ReceiptsPage.jsx` owns `search`/`activeFilters`/`isFiltered`/`showFilter` state and a single `fetchReceipts(filters, q)` that always re-derives `isFiltered` from the response rather than computing it locally. `ReceiptsFilter.jsx` is a collapsible panel (toggled by a "فلترة" button in `ReceiptsPage.jsx`'s header, styled blue with a dot indicator once a filter is active) with four cascading `FilterSearchableSelect` fields — contractor → authority (both from `getFilterOptions()`, `GET /api/receipts/filter-options`) → deal (`getDealsByContractorAndAuthority`, enabled only once both are picked) → branch (`getDealBranchesForReceipt`, enabled only once a deal is picked) — each selection resets the ones after it and clears their fetched option lists (done in the change handlers, not in the fetch `useEffect`s, so the `else` branch never calls `setState` synchronously inside an effect). `ReceiptsList.jsx` is purely presentational here too: no more `pagination`/`onPageChange` props, just an `isFiltered` prop that switches its empty-state message ("لا توجد وصولات بعد..." vs "لا توجد وصولات تطابق معايير الفلترة المحددة") and gates the "يتم عرض آخر 10 وصولات فقط..." hint (hidden once a filter is active).

**Receipts (الوصولات) — creating a receipt** — `ReceiptsPage.jsx` also follows the standard `*Page`/`*List`/`*Form`/`*DeleteModal` shape, plus a `selectedReceipt` state: when set, the page renders `ReceiptDetail.jsx` full-page (like `DealDetail.jsx`) instead of the list; `ReceiptsList.jsx`'s green eye button and row double-click both call `onView` → `setSelectedReceipt`. `ReceiptForm.jsx` is the interesting piece: creating a receipt is a 4-step cascading form (contractor+authority → deal → branch → date/reference), each step gated on the previous selection and fetched fresh via `receiptsService.js`:
  - Step 2 calls `getDealsByContractorAndAuthority` (`GET /api/receipts/deals?contractor_id=&authority_id=`) — only returns deals that already have both `deal_items` and `deal_branches` rows (a receipt can't be issued against a deal with no materials or no branches).
  - Step 3 calls `getDealBranchesForReceipt` (`GET /api/receipts/deal-branches/:dealId`).
  - Step 4 calls `getNextCounter` (`GET /api/receipts/next-counter/:dealId`) purely to preview the reference (`{deal_reference}-{counter}`) client-side; the authoritative counter/reference is recomputed server-side inside the same transaction that inserts the row, so a race between two clients can't produce a duplicate (the `UNIQUE(deal_id, counter)` constraint is the backstop).
  - `ReceiptForm` doubles as the edit form (`isEdit = Boolean(receipt)`): editing only exposes the branch + date fields (contractor/authority/deal render as read-only text) because `receiptsController.js`'s `update` only ever touches `receipt_date`/`branch_id` — matches the DB-level intent that a receipt's deal/contractor/authority are immutable once created.
  - Step transitions fade in via a `fade-in` keyframe added to `globals.css` (`animate-[fade-in_0.3s_ease-out]`) — the only custom animation utility in the project; reuse it rather than adding another one-off keyframe for future step-style forms.

`receiptsController.js`'s `create` runs inside a single `pool.connect()` transaction: look up the deal's `reference`, compute `counter = MAX(counter)+1` for that `deal_id`, call `createDealSnapshot(client, dealId)` (from `utils/dealSnapshot.js`), then insert. `createDealSnapshot` is idempotent — it no-ops if `deal_items_snapshot` already has rows for that deal — so it only actually runs on a deal's *first* receipt, copying each `deal_items` row's `min_quantity`/`max_quantity` into `initial_min_qty`/`initial_max_qty`/`remaining_qty` (a deal's original quantities must stay recoverable even after later receipts reduce what's left).

**Receipts — materials and quantity tracking** — `ReceiptDetail.jsx` shows the receipt's read-only info card (reference/contractor/authority/branch+wilaya+commune/date/`created_by_name`) then an always-visible add-material form (same "stays open after add" convention as `DealItems.jsx`) followed by the receipt's `receipt_items` table with an HT/TTC totals row. Materials are picked via a local `MaterialSearchableSelect` fed by `getAvailableMaterials(receiptId)` (`GET /api/receipts/:id/available-materials`) — this endpoint joins `deal_items` → `deal_items_snapshot` (falling back to `max_quantity` if no snapshot row exists yet) and excludes materials whose `remaining_qty` has hit 0; it also flags `already_in_receipt` per row so the frontend filters out materials already added to *this* receipt (the dropdown), while the add-form's info box surfaces `unit_price`/`tva`/`remaining_qty`/`initial_max_qty` for the selected material and a live "remaining after add" preview. Every quantity-mutating endpoint is a `pool.connect()` transaction in `receiptsController.js` that keeps `deal_items_snapshot.remaining_qty` in sync:
  - `addReceiptItem` (`POST /:id/items`) — validates the deal item belongs to the receipt's deal, rejects a duplicate material for the same receipt, calls `createDealSnapshot` defensively (in case this is the deal's first-ever receipt item), checks `quantity <= remaining_qty`, inserts the row (copying `unit_price`/`tva` from `deal_items` at that moment — a receipt line is a price snapshot, not a live FK read), then decrements `remaining_qty`.
  - `updateReceiptItem` (`PUT /:id/items/:itemId`) — restores the old quantity before checking the new one (`available = remaining_qty + old_quantity`) so shrinking a line doesn't falsely fail the bounds check.
  - `removeReceiptItem` (`DELETE /:id/items/:itemId`) — deletes the row and adds its quantity back to `remaining_qty`.
  - `getReceiptItems` (`GET /:id/items`) — joins `raw_materials`/`deal_items`/`material_categories` and computes `total_ht`/`total_ttc` in SQL, same pattern as `dealsController.js`'s `getDealStats`.

  Double-clicking a table row (or the row's own inline pencil-edit is *not* used for the modal — clicks are guarded with `!isEditing`) opens `ReceiptItemEditModal.jsx`: a small centered modal (not full-page) showing read-only material info and a quantity input whose max is `remainingQty` (looked up in the parent's `availableMaterials` list by `material_id`) plus the item's *current* quantity, since that quantity is already subtracted from `remaining_qty`. The modal owns no toast itself — its `onSuccess` callback is what triggers the parent's toast plus `fetchItems()`/`fetchAvailableMaterials()` refresh, matching how `ReceiptItemDeleteModal.jsx` (and `ReceiptDeleteModal.jsx` before it) also defer the success toast to the caller.

  **Hint text convention** — every "double-click to open/edit" or keyboard-shortcut hint below a table (`DealsList.jsx`, `ReceiptsList.jsx`, `ReceiptDetail.jsx`) is rendered the same way: `<div className="flex items-center justify-end gap-2 mt-2 px-4">` wrapping a bold `<span className="text-sm font-bold text-slate-600 dark:text-slate-300">` and a `lucide-react` `<Lightbulb size={16} className="text-yellow-500 shrink-0" />` (icon comes after the text in DOM order since RTL + `justify-end` places it visually on the right, matching the leading position it would have in a right-to-left sentence). Reuse this exact markup for any new hint rather than a plain `<p>`.

**Receipts — per-record ownership lock (edit/delete restricted to the creator)** — a receipt (and everything under it) can only be mutated by the user who created it, or by an admin; this is enforced on the backend and mirrored in the UI for UX only. `receiptsController.js`'s `checkReceiptOwnership(receiptId, req, res, message)` helper (`SELECT created_by FROM receipts WHERE id = $1`, then `created_by !== req.user.id && req.user.role !== "admin"` → 403 with the given Arabic message) gates `update` and `remove`. The three item-level mutators (`addReceiptItem`/`updateReceiptItem`/`removeReceiptItem`) can't reuse that helper as-is since they run inside their own `pool.connect()` transaction and must `ROLLBACK` before responding — they inline the same `created_by`/`role` check against the `client` right after `BEGIN` (added to the existing `SELECT deal_id ... FROM receipts` in `addReceiptItem`, and as a new `SELECT created_by FROM receipts` in the other two) rather than calling out to a pool-based helper mid-transaction. On the frontend, `ReceiptsList.jsx` and `ReceiptDetail.jsx` each independently compute `isOwner = receipt.created_by === getUser()?.id || getUser()?.role === "admin"` (no shared hook — same lightweight pattern as `UsersPage.jsx`'s admin gate) and swap Edit/Delete buttons for a static `Lock` icon (`lucide-react`) when `false`; `ReceiptDetail.jsx` additionally hides the always-visible add-material form entirely and shows an amber banner at the top of the page. This is UI-only defense-in-depth — the 403 is what actually stops the request, and `ReceiptDeleteModal.jsx`/`ReceiptItemEditModal.jsx`/`ReceiptItemDeleteModal.jsx` already surface any `error.arabicMessage` in their inline red alert box, so no modal-specific handling was needed for the new 403s.

**Receipts — Excel export and print (print currently disabled)** — `ReceiptDetail.jsx`'s header has a language `<select>` (`exportLanguage` state, `"AR"`/`"FR"`, default `"AR"`) next to a "تحميل Excel" button (`handleExportExcel`) calling `exportReceiptToExcel(receipt, items, exportLanguage)` from `src/lib/exportReceiptExcel.js`: it picks `livraisonAR.xlsx` or `livraisonFR.xlsx` by the `language` param and `fetch()`es the pre-designed template from `frontend/public/templates/` (loaded fresh per export, never mutated), fills fixed header cells (`A1`/`E1`/`A4`/`E3`/`G8`) plus one row per item starting at row 12 (copying that row's cell styles via a `safeCopyStyle` helper — deep-clones with `JSON.parse(JSON.stringify(...))` inside a try/catch so a style-clone failure can't abort the whole export), computes HT/TTC totals into the template's totals rows (originally rows 17/18, shifted down if there are more items than the template anticipates), merges `A:F` across the two totals rows for a centered bold "شكراً على ثقتكم" message, and clears every row below the totals (value/style/merges/height) so leftover template content can't bleed through. The whole function body is one try/catch that `console.error`s the message and stack before rethrowing, so failures surface in devtools instead of just the generic Arabic toast. On success `ReceiptDetail.jsx` shows a 5-second (longer than the usual 3.5 s) success toast telling the user to open the file and print with Ctrl+P — `showToast` takes an optional third `duration` param for this. Both `livraisonAR.xlsx` and `livraisonFR.xlsx` exist under `frontend/public/templates/`, and `exportReceiptToExcel` branches on `language` throughout: header cell addresses differ per template (e.g. `created_by_name` goes to `A1` for AR but `I1` for FR), the material name column pulls `item.name_lat || item.name_ar` for FR vs `item.name_ar` for AR, the thank-you message and generated filename are also language-specific — don't assume the two templates share cell positions when touching this function. A parallel `src/lib/printReceiptPDF.js` builds a standalone RTL HTML receipt (same header/materials/totals shape) and opens it in a new `window.open()` tab with `window.print()` auto-triggered on load — its "طباعة" button and `handlePrint` wiring are still in `ReceiptDetail.jsx` but the JSX button itself is commented out (`{/* PRINT BUTTON - disabled for now ... */}`) pending design sign-off; the import and handler are intentionally left in place for a quick re-enable.

**Receipts — cumulative Excel export (per deal + branch, over a date range)** — a second, independent export path from the one above, reached from `ReceiptsFilter.jsx` rather than `ReceiptDetail.jsx`: once both a deal and a branch are selected in the cascading filter, a green "تحميل Excel" button appears and opens `CumulativeExportModal.jsx` (day/month/year selects for a start/end date, defaulting to the first-of-month and today respectively, plus the same AR/FR language `<select>`). On submit it calls `getCumulativeItems(dealId, branchId, startDate, endDate)` (`GET /api/receipts/cumulative-items`, `verifyToken`-gated only — no `can_manage_receipts` requirement, since it's a read-only report) which requires all four query params (400 + Arabic message if any are missing) and returns `{ items, info, period }`: `items` is `receipt_items` **summed across every receipt** matching that `deal_id`+`branch_id`+`receipt_date` range, `GROUP BY` material/price/TVA (so the same material at two different prices across receipts yields two rows, not one); `info` is the deal/branch/authority/contractor header data (re-joined fresh, not reused from `ReceiptDetail.jsx`'s props since this isn't tied to any single receipt). The modal then calls `exportCumulativeExcel(data, language)` from `src/lib/exportCumulativeExcel.js` — a near-duplicate of `exportReceiptExcel.js` (same template files, same `startRow = 12`/rows-17-18-totals/`safeCopyStyle`/clear-below-totals logic) with three deliberate differences: quantities are `SUM(ri.quantity)` across receipts instead of one receipt's `quantity`; the `E1` "nbon" cell is explicitly set to `null` (there's no single receipt reference for a cumulative report) instead of a reference string; and `G8` (the date cell) is filled with **today's export date** (`DD/MM/YYYY`, computed client-side, not the filtered period) rather than a receipt date — the period range itself only surfaces in the generated filename (`تراكمي_{branch_name}_{start}_{end}.xlsx` / `Cumulatif_...`). The `A1`/`I1` user cell is filled from `getUser()?.full_name` (the currently logged-in user, from `lib/auth.js`) rather than `created_by_name`, since a cumulative report isn't attributed to one receipt's creator. If `getCumulativeItems` returns zero items, the modal shows an inline Arabic error ("لا توجد مواد موزعة في هذه الفترة") instead of exporting an empty workbook. This whole feature intentionally duplicates rather than parameterizes `exportReceiptExcel.js` — keep that in mind if the two ever need to be reconciled, but don't assume touching one updates the other.

**Invoices (الفواتير) — deriving an invoice from a period of receipts, not building one line by line** — unlike every other section, there's no `InvoiceForm.jsx`: an invoice is created by picking a contractor → authority → deal (`InvoicesFilter.jsx`'s three cascading `FilterSearchableSelect` fields, same component shape as `ReceiptsFilter.jsx`'s) plus a start/end date range (the same day/month/Arabic-month/year `<select>` triple used everywhere else, defaulting to first-of-month/today), then clicking "إنشاء فاتورة" — which calls `create()` directly with no item-entry step, because the backend derives the line items itself from `receipt_items` in that period (see the backend note below). `InvoicesFilter.jsx` is rendered **always visible** at the top of `InvoicesPage.jsx` (not toggled behind a "فلترة" button like `ReceiptsFilter.jsx` is), and does double duty as both the invoice-creation form and the list filter — "فلترة" filters the existing `InvoicesList.jsx` by the same three fields (no date range involved in filtering, only in creation), while "إنشاء فاتورة" is disabled until a deal and both dates are selected. On success `InvoicesPage.jsx`'s `handleCreated` refreshes the list in the background and immediately opens the new invoice's full detail view via a `getById` call (list rows from `getAll` don't carry `contractor`/`authority`/`items`, so viewing — whether just-created or double-clicked from the list — always re-fetches by id first). `InvoicesList.jsx` mirrors `ReceiptsList.jsx`'s shape exactly: `LIMIT 10` unfiltered / all-matching when `contractor_id`/`authority_id`/`deal_id` is set (`filtered` flag from the response, not computed client-side), the same ownership-lock pattern (`created_by === getUser()?.id || role === "admin"`, `Lock` icon otherwise gating only the delete button — there's no edit at all, invoices are immutable once created), and the same double-click-row / "hint text" conventions. `InvoiceDetail.jsx` is a full-page view (not a modal) showing two complete info cards (every `contractors`/`contracting_authorities` column, 2-column responsive grid, `fax` only rendered `if (contractor?.fax)`/`if (authority?.fax)` since it's nullable) above the `invoice_items` table and an HT/TTC totals row plus two summary cards; its "تحميل Excel" button is present but permanently `disabled` with a `title` tooltip ("سيتم تفعيل هذه الخاصية قريباً") — no `exportInvoiceExcel.js` exists yet, this is intentionally unwired pending a template like `livraisonAR.xlsx`. `created_by_name` (from the `FULL_SELECT` join) surfaces in two places: as an `InvoicesList.jsx` column (`hidden md:table-cell`, placed right before the actions column) and as a `Users`-icon line in `InvoiceDetail.jsx`'s header, below the invoice-date/period line. `InvoiceDeleteModal.jsx` also independently computes `isOwner` (same `getUser()` check as the list) rather than relying solely on the list hiding its own delete button — it shows an amber "created by another user" notice and disables the confirm button when `!isOwner`, so the modal is safe even if it's ever opened from somewhere that skipped the list's own gating.

Backend: `controllers/invoicesController.js` — see the backend section below for the derivation/transaction details.

**Users, auth, and per-record `created_by` tracking** — the users section follows the standard `*Page`/`*List`/`*Form`/`*DeleteModal` shape plus two extras: `ResetPasswordModal.jsx` (password changes are a separate admin action from editing a user, matching the backend's separate `PUT /:id/reset-password` endpoint) and a client-side admin gate — `UsersPage.jsx` reads `getUser()` itself and renders an Arabic "admin only" message instead of the list for non-admins, as a UX nicety in front of the backend's real `requireAdmin` enforcement (a non-admin who somehow reaches this page still gets 403s from every call, not just a hidden button). `UserForm.jsx` doubles as add/edit (`isEdit = Boolean(user)`): `username`/`password` only appear on create (editing a user never touches credentials — that's what `ResetPasswordModal` is for), the permissions checklist (with "تحديد الكل"/"إلغاء الكل" bulk buttons) only renders when `role === "secondary"` since `admin` implies every `can_manage_*` flag, and `is_active` only appears on edit (a brand-new user is always active). Because `usersService.getAll()` has no pagination (mirrors the backend, which returns the full user list — the assumption being a handful of staff accounts, not thousands), `UsersPage.jsx` does its own client-side filter over `full_name`/`username` rather than round-tripping `page`/`search` query params like every other section's list.

Backend: `middleware/auth.js` was rewritten from a Supabase-JWT `authenticate()` stub (unused, and `routes/users.js` previously called the Supabase Admin API directly with no local `users` table at all) into the real app-level auth for the `users` table created in `014_users.sql`: `verifyToken` (extracts `Bearer` token, `jwt.verify`s it against `config/auth.js`'s `JWT_SECRET`, then re-fetches the user row fresh from the DB by the token's `id` — not just trusting the JWT payload — so a deactivated (`is_active = false`) account is locked out immediately rather than only after its token expires), `requireAdmin` (403 unless `role === "admin"`), and `requirePermission(permission)` (403 unless admin or `user[permission] === true`; the seven `can_manage_*` columns on `users` map 1:1 to the seven manageable sections — there's deliberately no `can_manage_material_categories`, since that's a raw-materials sub-resource gated by `can_manage_raw_materials`). `utils/password.js` wraps `bcrypt` (salt rounds 10); `controllers/authController.js` (`login`/`getMe`/`changePassword`) issues/consumes the JWT — the token payload and every "safe" user read always run through the same `buildPermissions()`/`SAFE_COLUMNS` shape so `password_hash` can never leak into a response. `controllers/usersController.js` is `requireAdmin`-gated end to end (`routes/users.js`) and self-joins `users` to itself (`LEFT JOIN users creator ON creator.id = u.created_by`) for `created_by_name` — the same table doubles as its own audit trail. `remove()` blocks deleting your own account and checks `created_by` across `deals`/`contracting_authorities`/`contractors`/`authority_branches`/`receipts`/`raw_materials`/`users` before allowing a delete (a user who has ever created *anything*, including another user, can't be removed).

Every other section's routes now chain `verifyToken` on every route and `requirePermission("can_manage_<section>")` on the mutating ones (`create`/`update`/`remove`, plus deals' and receipts' sub-resource routes) — see `routes/deals.js`, `routes/receipts.js`, `routes/rawMaterials.js`, `routes/materialCategories.js` (shares `can_manage_raw_materials`, no permission of its own), `routes/contractingAuthority.js`, `routes/contractors.js`, `routes/authorityBranches.js`. Their controllers' `create` functions now insert `created_by = req.user.id` (only possible because `verifyToken` runs first and populates `req.user`), and their `getAll`/`getById` queries `LEFT JOIN users` to surface `created_by_name` alongside the existing joins — `dealsController.js` and `receiptsController.js` just added `u.full_name AS created_by_name` to their existing `FULL_SELECT`-style multi-join queries rather than adding a new query shape. `routes/invoices.js`/`backup.js` remain stubs and are not wired to auth yet — do that when a controller lands for them.

### Backend (`backend/src/`)

`server.js` imports all route files and mounts them under `/api/<section>`. Logic lives in `controllers/` — routes are thin and only wire up multer and call the controller.

- `config/db.js` — exports a `pg.Pool`. **Critical quirk #1:** Supabase wraps passwords that contain special characters in `[...]` in the connection string — `db.js` strips those brackets before passing credentials to pg. **Critical quirk #2:** `pg` parses `DATE` columns (OID `1082`) into local-timezone JS `Date` objects by default, which then serialize to a UTC ISO string shifted back a day (e.g. `2026-01-01` → `2025-12-31T23:00:00.000Z`) whenever the server's local timezone is ahead of UTC. `db.js` overrides that type parser to keep `DATE` values as the raw `"YYYY-MM-DD"` string — don't remove this, and don't reintroduce `new Date(...)`/`.toISOString()` round-trips for date fields anywhere in the stack (controllers or frontend forms should build/parse date strings manually, see the date-picker pattern below).
- `controllers/rawMaterialsController.js` — the reference implementation for all future controllers: pagination+search on GET, input validation returning Arabic error messages, Supabase Storage upload via service-role client. `materialCategoriesController.js`, `contractingAuthorityController.js`, `authorityBranchesController.js`, and `contractorsController.js` follow the same shape (list with `page`/`search` query params + pagination envelope, `getById`, `create`/`update` with shared field validation, `remove`) — none of them use Storage upload, only `rawMaterialsController.js` does.
- `controllers/contractorsController.js`, `contractingAuthorityController.js`, and `rawMaterialsController.js` additionally accept an optional `limit` query param (default `10`, capped at `1000`) on `getAll` — used by `DealForm.jsx`/`DealItems.jsx` to pull the full list for their searchable-select dropdowns instead of just one paginated page.
- `controllers/dealsController.js` — first controller to `JOIN` across tables: `getAll`/`getById` join `contractors` and `contracting_authorities` to return `contractor_name`/`authority_name` alongside the deal row. `create`/`update` validate that `end_date` is strictly after `start_date` and translate the `23505` unique-violation Postgres error code (duplicate `reference`) into an Arabic message. It also owns two join-table sub-resources, both mounted in `routes/deals.js` **before** the `/:id` routes:
  - `getDealBranches`/`addBranchToDeal`/`removeBranchFromDeal` (`/api/deals/:id/branches`) — `removeBranchFromDeal` refuses to remove a deal's last remaining branch.
  - `getDealItems`/`addDealItem`/`updateDealItem`/`removeDealItem` (`/api/deals/:id/items`) — the deal's material/pricing lines (`deal_items` table). `addDealItem` validates required fields, `min_quantity < max_quantity`, `0 ≤ tva ≤ 100`, `unit_price > 0`, and translates the `23505` unique-violation (duplicate `material_id` per deal) into an Arabic message; `updateDealItem` only updates `tva`/`min_quantity`/`max_quantity`/`unit_price` (material/category aren't editable after creation). `getDealItems` additionally `LEFT JOIN`s `deal_items_snapshot` for `initial_max_qty`/`initial_min_qty`/`remaining_qty` (see the "remaining-quantity tracking" note above). `removeDealItem` checks `SELECT COUNT(*) FROM receipt_items WHERE deal_item_id = $1` before deleting — a deal item already delivered against in a receipt can't be removed (HTTP 400, Arabic message); `DealItems.jsx`'s delete-confirmation modal keeps itself open on that 400 and renders the message inline instead of closing/toasting, unlike every other section's delete modal.
  - `getDealStats` (`/api/deals/:id/stats`) — read-only aggregation over `deal_items`, no new table/migration involved. Computes HT (`quantity × unit_price`) and TTC (`× (1 + tva/100)`) totals per item and deal-wide in SQL, returning `{ items, totals, deal }`. Backs `DealStats.jsx`'s summary cards, detail table, and Excel export.
  Use this controller as the reference for any future section with FK relationships (`invoices`).
- `config/auth.js` — `{ JWT_SECRET, JWT_EXPIRES_IN: "8h" }`, both read at require-time. `JWT_SECRET` must be set in `.env`/`.env.example` (no fallback — the app will sign/verify with `undefined` if it's missing, so this is a real startup requirement, not an optional one).
- `middleware/auth.js` — real app-level JWT auth (replaced an earlier Supabase-JWT `authenticate()` stub that was never wired to any route). Exports `verifyToken`, `requireAdmin`, `requirePermission(permission)` — see the Users/auth note in the Frontend section above for the full behavioral rundown. Every route file except `routes/auth.js`'s own `/login` chains `verifyToken` first.
- `middleware/validation.js` — a generic Joi-schema `validate()` wrapper. Scaffolded but unused; controllers currently do validation inline instead (see `rawMaterialsController.js`).
- `controllers/authController.js` / `routes/auth.js` — `POST /api/auth/login` (public), `GET /api/auth/me` / `PUT /api/auth/change-password` (both `verifyToken`-gated). `login` and `getMe` share a `buildPermissions(user)` helper so the JWT payload and every "current user" response use the identical `{ can_manage_deals, ... }` shape, computed as all-`true` for `role === "admin"`.
- `controllers/usersController.js` / `routes/users.js` — replaced the old Supabase-Admin-API-based stub now that `users` (migration `014`) is a real pg table. Fully `requireAdmin`-gated. See the Users/auth note in the Frontend section above.
- `utils/password.js` — `hashPassword`/`comparePassword`, thin `bcrypt` wrappers (salt rounds 10). Used by `authController.js` and `usersController.js`; never call `bcrypt` directly elsewhere.
- `routes/rawMaterials.js` — declares `/upload-image` **before** `/:id` to prevent route conflict; uses multer memory storage (5 MB limit, images only). Now also `verifyToken`/`requirePermission("can_manage_raw_materials")`-gated like every other mutating route (see the Users/auth note above).
- `controllers/receiptsController.js` — the receipts section (migrations `013`, `016`), backed by `deals`/`contractors`/`contracting_authorities`/`authority_branches` joins (`FULL_SELECT` constant shared by `getAll`/`getById`/`create`/`update`, including `branch_wilaya`/`branch_commune` for `ReceiptDetail.jsx`'s info card, and `c.phone_mobile AS contractor_phone` — `contractors` has no plain `phone` column, only `phone_fixed`/`phone_mobile` — for the Excel export/print templates). `getAll` builds its `WHERE` clause conditionally from `search`/`contractor_id`/`authority_id`/`deal_id`/`branch_id` query params and only appends `LIMIT 10` when none of the four FK filters are present — see "Receipts — default view and filtering" above; it returns `{ data, total, filtered }`, not the `{ data, pagination }` envelope every other section's `getAll` uses. `getFilterOptions` (`GET /api/receipts/filter-options`) returns `{ contractors, authorities }` for the filter panel's first two dropdowns. Mounts lookup/sub-resource routes in `routes/receipts.js` **before** `/:id` (`/filter-options`, `/deals`, `/deal-branches/:dealId`, `/next-counter/:dealId`, `/cumulative-items`, and the `/:id/items*`/`/:id/available-materials` group) that back the frontend — see the Frontend section above. `getCumulativeItems` (`GET /cumulative-items`, query params `deal_id`/`branch_id`/`start_date`/`end_date`, all required) is the one receipts endpoint that aggregates across multiple receipts rather than reading a single one — see "cumulative Excel export" above. `create` generates `reference = "{deal.reference}-{counter}"` and calls `createDealSnapshot()` inside a `pool.connect()` transaction; `update` only allows changing `receipt_date`/`branch_id`. `remove()` blocks deletion (HTTP 400, Arabic message) if the receipt still has `receipt_items` rows. A second `RECEIPT_ITEMS_SELECT` constant (joining `raw_materials`/`deal_items`/`material_categories`, computing `total_ht`/`total_ttc`) backs `getReceiptItems`/`getDealMaterialsForReceipt`/`addReceiptItem`/`updateReceiptItem`/`removeReceiptItem` — see the "materials and quantity tracking" note above for the transaction details.
- `controllers/invoicesController.js` — the invoices section (migration `017`). An invoice isn't hand-built line by line like a deal or receipt: `create` (`POST /api/invoices`, body `{ deal_id, contractor_id, authority_id, start_date, end_date }`) derives its own line items by re-running the same cross-branch cumulative aggregation query `getCumulativeItemsForInvoice` exposes read-only (both share the `fetchCumulativeItems(queryable, dealId, startDate, endDate)` helper, called with `pool` for the read-only endpoint and with the transaction's `client` inside `create` — unlike the receipts cumulative export, this one has **no `branch_id` filter**, since an invoice covers every branch a deal delivered to in the period). If that query returns zero rows, `create` rolls back and returns HTTP 400 (`"لا توجد مواد موزعة في هذه الفترة لإنشاء فاتورة"`) rather than inserting an empty invoice. On success it snapshots each aggregated row into its own `invoice_items` row (`name_ar`/`name_lat`/`unit`/`category_name`/`unit_price`/`tva` copied at creation time, not live FK reads — same "receipt line is a price snapshot" philosophy as `receipt_items`), computes `counter = MAX(counter)+1 WHERE deal_id = $1` and `reference = "{deal_reference}-F{counter}"` (the `-F` distinguishes it from a receipt's `{deal_reference}-{counter}` pattern), and stores the totals on the `invoices` row itself (`total_ht`/`total_ttc`) rather than recomputing them from `invoice_items` on every read. `getById` additionally fetches the full `contractors`/`contracting_authorities` rows (not just the joined `_name` columns `getAll` uses) plus `invoice_items`, and returns them nested as `{ ...invoice, contractor, authority, items }` — `InvoiceDetail.jsx` renders every contractor/authority field from those nested objects, unlike `ReceiptDetail.jsx` which only ever shows a handful of joined columns. `getDealsByContractorAndAuthority` (`GET /invoices/deals`) only returns deals with `EXISTS (... receipts r JOIN receipt_items ri ...)` — a deal with zero delivered materials can't have an invoice drafted against it. `remove` is ownership-gated the same way as `receiptsController.js`'s `checkReceiptOwnership` (inlined here since it also needs to `ROLLBACK` mid-transaction), and deletes `invoice_items` before the `invoices` row itself — there's no downstream table referencing invoices yet, so no `Deletion Protection Rules` check is needed on `remove`. Mounts `/filter-options`, `/deals`, `/cumulative-items` in `routes/invoices.js` **before** `/:id`, mirroring receipts; only `create`/`remove` are `requirePermission("can_manage_invoices")`-gated, the read endpoints are `verifyToken`-only.
- `routes/backup.js` — **stub routes**, not yet backed by a controller or migration, and not yet wired to `verifyToken`/`requirePermission`. Returns `{ message: "... — to be implemented" }` placeholders. Follow the "Adding a New Section" pattern below to flesh it out, and add auth wiring per the Users/auth note above when you do.
- `utils/email.js` — `sendEmail()` stub used by `routes/backup.js`; only logs to console, no provider (nodemailer/Resend/SendGrid) configured yet.
- `utils/tableExists.js` — `tableExists(client, tableName)` checks `information_schema.tables` before querying a table that may not exist yet; used by controllers' `remove`/`delete*` functions to guard forward-looking relationship checks against tables that haven't landed (currently only relevant to `routes/invoices.js`/`backup.js`'s stub tables). `deal_items`, `receipts`, and `receipt_items` are all real tables now (migrations `011`/`013`/`016`) — controllers query them directly without this guard. See [Deletion Protection Rules](#deletion-protection-rules).
- `utils/dealSnapshot.js` — `createDealSnapshot(client, dealId)`, called from `receiptsController.js`'s `create`. Idempotent (no-ops if `deal_items_snapshot` already has rows for the deal), so it only actually populates on a deal's first receipt — copies each `deal_items` row's `min_quantity`/`max_quantity` into `deal_items_snapshot.initial_min_qty`/`initial_max_qty`/`remaining_qty`. Takes the transaction's `client`, not the shared `pool`, so it participates in the caller's transaction.

### Database

Migrations are plain SQL in `database/migrations/`, numbered `001_`, `002_`, …. The runner at `database/scripts/run_migration.js` reads `DATABASE_URL` from `frontend/.env.local`, parses the password bracket-stripping itself, and accepts the filename as a CLI argument.

**Table conventions:**
- `id SERIAL PRIMARY KEY` (sequential integer, never UUID)
- `created_at` / `updated_at` as `TIMESTAMPTZ NOT NULL DEFAULT now()`
- `updated_at` kept current by the shared `set_updated_at()` trigger function (defined once in `001_`)
- RLS enabled; policy name `authenticated_full_access` grants full access to the `authenticated` role

**Migrations applied:**

This bit again with `012`/`013`: the receipts feature spec that introduced `deal_items_snapshot` and `receipts` originally asked for `011_deal_items_snapshot.sql`, but `011` was already `deal_items` — they were created as `012`/`013` instead. And again with `014`/`015`: the users/auth feature spec asked for `013_users.sql`, but `013` was already `receipts` — created as `014`/`015` instead. And again with `016`: a later receipts feature spec asked for `015_receipt_items.sql`, but `015` was already `add_created_by` — created as `016` instead. This will keep happening — always `ls database/migrations/` first.

**Seeded admin credentials — must be rotated in any real deployment:** `014_users.sql` inserts username `admin` / password `Admin@1234` (a real bcrypt hash, generated once via `bcrypt.hash("Admin@1234", 10)` at migration-authoring time — not the placeholder-looking string from the original feature spec, which was not a working hash). Change this password immediately after first login in any environment that isn't a disposable local dev database.

## UI Rules

- **Arabic UI, English code** — all visible text in Arabic, all identifiers/variables in English.
- **RTL throughout** — `dir="rtl"` on `<html>`. Sidebar is on the **right**; flex row order is reversed from LTR conventions.
- **Tailwind + inline style for dynamic colors** — use Tailwind for all static styles; use `style={{ backgroundColor: color + "18" }}` only when the color comes from the `sections[]` array at runtime. No CSS modules.  Every new component must use responsive prefixes (`sm:`, `md:`, `lg:`).
- **Font** — Tajawal via Google Fonts in `layout.js`. No other font should be introduced.
- **Section color** — each section has a hex color defined in the `sections[]` array in `page.js`. Use it (with opacity suffix like `+ "18"`) for icon backgrounds in that section's components.
- **Toast notifications** — implemented as local state in `*Page` components (`setTimeout` dismiss after 3.5 s), positioned with `fixed bottom-6 left-1/2 -translate-x-1/2`. Green for success, red for error.

## Dark Mode

Class-based dark mode (not OS `prefers-color-scheme`), toggled manually and persisted in `localStorage`.

- **No `tailwind.config.js`** — this is Tailwind v4, configured entirely in CSS. Dark mode is enabled via `@custom-variant dark (&:where(.dark, .dark *));` in `src/app/globals.css`, which makes every `dark:` utility apply based on a `.dark` class on `<html>` instead of the OS theme.
- **`ThemeProvider`** (`src/components/layout/ThemeProvider.jsx`) — client-side context wrapping the whole app from `layout.js`. Exposes `useTheme()` → `{ theme, toggleTheme }`. `toggleTheme` flips the class on `document.documentElement`, updates state, and writes `localStorage.setItem('theme', ...)`.
- **`ThemeToggle`** (`src/components/layout/ThemeToggle.jsx`) — Sun/Moon icon button (lucide-react) in the header next to the user avatar; consumes `useTheme()`. Copy this component's pattern (context consumer, not prop-drilled) for any other theme-aware control.
- **Anti-flash script** — see the `layout.js` bullet above; this is why `<html>` needs `suppressHydrationWarning`.
- **Styling convention for new/edited components** — every `bg-white`/`bg-slate-*`/`text-slate-*`/`border-slate-*` utility must have a matching `dark:` variant alongside it. The established shade mapping (light → dark) used across every section:
  - `bg-white` → `dark:bg-slate-800` (cards, modals, forms) · `bg-slate-50` → `dark:bg-slate-900` (page background) or `dark:bg-slate-700` (nested surfaces, inputs, secondary buttons)
  - `border-slate-200` → `dark:border-slate-700` · `border-slate-100` → `dark:border-slate-700`
  - `text-slate-800` → `dark:text-slate-100` · `text-slate-600`/`700` → `dark:text-slate-300` · `text-slate-400` → `dark:text-slate-500` · `text-slate-300` → `dark:text-slate-600`
  - `hover:bg-slate-50`/`100` → `dark:hover:bg-slate-700`/`600`
  - `placeholder:text-slate-400` → `dark:placeholder:text-slate-500`
  - Modal overlays `bg-black/30` → also add `dark:bg-black/50`
- **Never** add a `dark:` variant to a section's accent-color inline `style={{ backgroundColor: section.color }}` (or `+ "18"` opacity suffix) — accent colors are identical in both themes; only slate-based Tailwind utility classes get dark variants.

## UI Table Standards

Applies to every table component (existing and future) across all sections.

### Table Layout:
- Always use `table-fixed` and `w-full` on the table element
- Always wrap the table in a div with `overflow-x-auto` and `w-full`

### Table Header `<th>`:
- `font-bold text-base tracking-wide`
- `px-3 py-3 text-right whitespace-nowrap`
- Keep section color for background

### Table Data `<td>`:
- `font-medium text-sm text-slate-800`
- `px-3 py-3 text-right`
- `whitespace-nowrap overflow-hidden text-ellipsis`

### Table Rows `<tr>` in `tbody`:
- `border-b border-slate-100`

### General:
- Every table must have an empty state message in Arabic
- Every table must have a loading spinner during API calls
- Every table must have a search bar
- Action buttons: edit (blue), delete (red)
- Every color utility class (backgrounds, borders, text) needs its `dark:` counterpart — see [Dark Mode](#dark-mode)
- Full RTL support at all times
- Make sure all new UI components are fully responsive for mobile screens using Tailwind CSS responsive prefixes (`sm:`, `md:`, `lg:`). Full RTL support must be maintained.

## Adding a New Section (pattern to follow)

1. **Backend:** create `controllers/<section>Controller.js` mirroring `rawMaterialsController.js`; update `routes/<section>.js` to import from it. Chain `verifyToken` on every route and `requirePermission("can_manage_<section>")` on the mutating ones (unless the section is a sub-resource of an existing one, like `material_categories` under `can_manage_raw_materials`) — see the Users/auth note above. If the table needs creator tracking, add a `created_by INTEGER REFERENCES users(id)` column in its migration, set `created_by = req.user.id` in `create`, and `LEFT JOIN users` for `created_by_name` in `getAll`/`getById`.
2. **Frontend:** create `src/services/<section>Service.js`; create `src/components/<section>/` with `*Page`, `*List`, `*Form`, `*DeleteModal`.
3. **`page.js`:** add an `activeSection === "<section-id>"` branch in the main content area rendering `<*Page activeService={activeService} onServiceChange={setActiveService} />`.
4. **Database:** add `database/migrations/00N_<section>.sql` following the table conventions above; run it with the migration script.

**Adding a sub-section within an existing section** (e.g. material categories inside raw materials):
- Create a `categories/` subfolder under the section's component directory with its own `*Page`, `*List`, `*Form`, `*DeleteModal`.
- Add `showCategories` state to the parent `*Page`; render `<SubPage />` when true with a breadcrumb back button (no changes to `page.js` needed).
- The sub-section's `*Page` is self-contained: it owns its own fetch/toast/modal state and does not receive `activeService` props.

## Deletion Protection Rules

- NEVER delete a record that is linked to another table
- Always check relationships before deleting in the controller
- Return HTTP 400 with Arabic error message if record is linked
- Frontend delete modals must handle HTTP 400 and show Arabic error
- Use `tableExists()` helper (`backend/src/utils/tableExists.js`) before querying future tables
- This rule applies to ALL tables in the project
- `raw_materials` has no `category_id` column — a material's category only exists per deal line, on `deal_items.category_id`. `materialCategoriesController.js`'s `deleteCategory` check queries `deal_items.category_id` directly; don't reintroduce a join through `raw_materials` for this (an earlier version tried that and could never actually match anything).
- Now that `receipts` is a real table, both `dealsController.js`'s `remove` and `authorityBranchesController.js`'s `deleteBranch` also check `SELECT COUNT(*) FROM receipts WHERE deal_id = $1` / `WHERE branch_id = $1` (in addition to their pre-existing `deal_branches`/`deal_items` checks) before allowing a delete. `receiptsController.js`'s own `remove` follows the same rule one level down: it checks `SELECT COUNT(*) FROM receipt_items WHERE receipt_id = $1` before allowing a receipt to be deleted. One level down from that, `dealsController.js`'s `removeDealItem` checks `SELECT COUNT(*) FROM receipt_items WHERE deal_item_id = $1` — a single deal item can't be removed once any receipt has drawn against it, even if the deal itself has no other blockers.
- `usersController.js`'s `remove` applies this rule to users too, but checks `created_by` (not a direct FK the way `deal_id`/`branch_id` are) across all six tables that gained a `created_by` column in `015_add_created_by.sql`, **plus `users` itself** — a user who has ever created another user can't be deleted either. It also has one rule unique to this table: a user can never delete their own account (`req.user.id === req.params.id`), checked before the created-records scan.

## API Route Conventions

| Section              | Base path                     |
|----------------------|-------------------------------|
| Auth                 | `/api/auth`                   |
| Raw Materials        | `/api/raw-materials`          |
| Material Categories  | `/api/material-categories`    |
| Contracting Auth.    | `/api/contracting-authority`  |
| Authority Branches   | `/api/authority-branches`     |
| Contractor           | `/api/contractors`            |
| Deals                | `/api/deals`                  |
| Receipts             | `/api/receipts`               |
| Invoices             | `/api/invoices`               |
| Users                | `/api/users`                  |
| Backup               | `/api/backup`                 |

CORS is locked to `FRONTEND_URL` (defaults to `http://localhost:3000`).

Every route except `POST /api/auth/login` requires a valid `Bearer` token (`verifyToken`); mutating routes (`POST`/`PUT`/`DELETE`) on every section above additionally require the matching `can_manage_*` permission or `admin` role (`requirePermission`) — see the Users/auth note in the Frontend Architecture section for the full picture. `/api/users/*` is `requireAdmin`-gated end to end, including its `GET` routes.
